# 테크 스펙(의도 문서) 프로세스

PR 리뷰의 기준은 diff가 아니라 **의도 문서**다. seep은 지라·노션 없이 **GitHub Issue 본문을 테크스펙으로 쓴다.**
태스크를 시작할 때 이슈를 만들고 요약·요구사항·TC를 먼저 적는다. 이후 단계(테스트 도출, PR 본문, 드리프트 확인)는 모두 이 이슈를 기준으로 한다.

## 구조

```
GitHub Issue #12  (team-seep/seep-ios)          ← 단일 진실 소스
  ├─ 본문: 요약 / 요구사항 / TC-1..n / 기타
  ├─ 브랜치: feature/GH-12-{설명}  (git-flow, develop 기반)
  ├─ 테스트: test_GH12_TC{n}_{조건}_{기대결과}()
  └─ PR: 본문 "의도"에 Closes #12
```

- **이슈 번호가 곧 티켓 키다.** 표기: 문서·커밋·브랜치는 `GH-12`, 테스트 메서드는 하이픈 없이 `GH12`.
- 이슈 템플릿: `.github/ISSUE_TEMPLATE/idea.yml`(AI 추천·직접 기획안 → 승인 후 테크스펙으로 구체화, `docs/process/planning.md`), `feature.yml`(기능), `bug.yml`(버그). 새 이슈 화면에서 고르면 섹션이 채워진다.

## 이슈 본문 템플릿

| 섹션 | 내용 |
|---|---|
| 1. 요약 | 배경 · 목표 · 디자인(피그마 링크, 있으면) |
| 2. 요구사항 | 이 이슈를 처리하기 위한 요구사항 불릿. PR의 드리프트 확인이 이 목록과 diff를 대조한다 |
| 3. 테스트 케이스 (TC) | 사용자 관점 케이스를 한 줄씩 `TC-1`, `TC-2`… **ID는 바꾸지 않는다.** 각 TC는 유닛 / 자동화 / 수동 중 하나 이상에 배정된다(`docs/process/testing.md`). 작성 시점에 계층을 몰라도 되고, 테스트 도출 단계에서 Claude가 제안해 승인받는다. 구현하다 케이스가 늘면 코드에 임의 번호를 만들지 말고 **이슈에 TC를 먼저 추가**한다 |
| 기타 | 범위 밖, 참고 링크, 열린 질문 |

TC 한 줄 예:
```
- TC-1: 위시를 완료하면 해당 위시의 예약된 로컬 알림이 모두 취소된다
- TC-2: 완료 처리에 실패하면 알림은 그대로 남고 에러 알럿이 뜬다
- TC-3: 앱 업데이트(schemaVersion 3→4) 후 기존 위시가 그대로 보인다
```

## Claude로 만들기

```
GH-12 이슈 테크스펙 써줘: {하고 싶은 것 한두 줄}
```
Claude는 관련 코드를 읽고 위 템플릿대로 요약·요구사항·TC 초안을 만든 뒤 `gh issue create`(또는 `gh issue edit 12 --body-file`)로 올린다. **이슈 생성·수정 전에 본문을 보여주고 확인받는다.**

## 예외

- **핫픽스**(`hotfix/`): 이슈 생략 가능. PR 본문 "의도"에 장애 내용 1줄 + 재현 경로를 적고 풀코스로 취급.
- **릴리즈**(`release/`): 버전·빌드 번호만 바뀌면 이슈 없이 경량.
- **문서·CI만 바꾸는 작업**: 이슈 없이 `NO-ISSUE`로 진행 가능. 대신 PR "의도"에 한 줄 설명.
